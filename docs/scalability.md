# 1,000개 이상 데이터 처리 분석 (#16)

## 측정 방법과 실제 결과

- 수정된 코드를 Python 3.12.14, Linux x86_64에서 실행했습니다. 사용자 Windows 실행 결과가 아닙니다.
- 기본 퀴즈를 복제하되 문제 번호를 달리한 생성 데이터 1,000개와 10,000개를 사용했습니다. 기록은 0개입니다.
- 각 크기별 5회 측정의 중앙값이며, 임시 폴더를 사용하므로 실제 state.json을 변경하지 않습니다.
- 저장 시간은 검증, 이전 데이터 백업, JSON 직렬화, flush/fsync 및 파일 교체를 포함합니다.
- 메모리는 tracemalloc으로 게임 불러오기와 Quiz 객체 생성 동안의 Python 할당 최고치를 측정했습니다. 전체 프로세스 RSS나 시스템 메모리 전체가 아닙니다.
- 디스크 캐시, CPU, 저장 장치 및 기록 길이에 따라 달라지며 사용자 컴퓨터의 성능을 보장하지 않습니다.

## 현재 구조의 시간·메모리 비용

N은 문제 수, H는 게임 기록 수, S는 JSON 전체 바이트 수, K는 고른 문제 수입니다. 문자열 길이와 선택지 개수도 실제 비용에 영향을 줍니다.

| 동작 | 현재 비용과 한계 | 대응 |
|---|---|---|
| 시작 | JSON 전체를 읽고 검증하며 객체를 생성. 대략 O(S + N + H), 메모리 O(S + N + H) | 1,000/10,000개 실측. JSON과 객체가 동시에 존재할 수 있음을 인정 |
| 목록 출력 | 이전에는 N개 전체를 화면에 출력 | 현재 20개씩 표시. 한 쪽 출력 O(20), 페이지용 전체 복사 없음 |
| 기록 조회 | H개 전체 출력은 긴 대기와 스크롤 유발 | 최신순 20개씩 출력, 역순 전체 리스트 복사 없음 |
| 정답 확인 | 정답 번호 비교 O(1) | 유지 |
| 번호로 문제 선택 | 리스트 인덱스 접근 O(1) | 페이지가 바뀌어도 전체 번호 유지 |
| 무작위 선택 | random.sample 사용. 추가 공간은 통상 선택 목록 O(K), 내부 전략은 선택 비율에 따라 달라짐 | 선택 문제 수만 풀이, 단순히 항상 O(K) 시간이라고 보장하지 않음 |
| 삭제 | 리스트 뒤 항목 이동 때문에 최악 O(N) | 현재 규모에서는 유지, 저장 비용도 함께 고려 |
| 저장 | 전체 검증·이전 파일 로드·백업·직렬화·교체. O(S + N + H) | 변경 없는 저장은 쓰기 생략. 최초 정상 스냅샷이 없을 때는 백업 생성 |
| 기록 누적 | H가 계속 증가하면 시작과 저장 비용도 증가 | 현재 기록을 잘라 버리지 않음. 장기 운영 시 별도 보관 설계 필요 |

1,000개 실측에서는 JSON 전체 저장·로드 구조를 유지할 근거를 얻었지만, 10,000개에서는 시간과 메모리가 커집니다. 100,000개나 동시 사용자 환경은 측정하지 않았습니다.

## 검색 속도와 인덱싱 검토

현재 메뉴에 텍스트 검색 기능은 없습니다. 따라서 검색 기능이 빠르다고 주장하지 않습니다.
추가한다면 단순 부분문자열 검색은 문제와 문자열을 순회하므로 대략 O(N × 평균 문자열 길이)입니다.
빈번한 ID 조회는 고유 ID와 dict 인덱스로 평균 O(1)을 목표로 할 수 있으나 인덱스 메모리 O(N) 및 추가·삭제 시 갱신이 필요합니다.
키워드 검색은 역색인 또는 표준 라이브러리 sqlite3의 테이블/인덱스를 검토할 수 있습니다. 일반 B-tree 인덱스가 모든 부분문자열 검색을 자동으로 빠르게 만들지는 않습니다.

## 페이징·파일 분할·SQLite 비교

| 방안 | 장점 | 비용 및 채택 여부 |
|---|---|---|
| 화면 페이징 | 한 번에 출력할 양 감소 | 현재 구현. 전체 JSON 로드 메모리까지 줄여주지는 않음 |
| 문제/기록 파일 분할 | 바뀐 부분만 저장 가능 | 파일 간 일관성·복구가 복잡. 과제의 루트 state.json 규칙을 지키기 위해 현재 미채택 |
| 기록을 날짜별 보관 | 오래된 기록 때문에 주 파일이 커지는 문제 완화 | 내보내기·복원 정책 필요. 현재 미구현 |
| SQLite 저장 | 부분 조회·인덱싱·트랜잭션 지원 | 현재 JSON 규칙과 충돌하므로 저장소 교체 미채택. 후속 서비스에서 검토 |
| SQLite 검색 캐시 | JSON을 원본으로 유지하며 검색 보조 | 캐시 재생성·동기화 정책 필요. 현재 미구현 |

정상 백업은 5개까지 보관하므로 정상 백업 용량은 대략 5 × S입니다. 손상 원본과 수동 복원 전 사본은 자동 삭제하지 않아 추가 디스크 공간이 필요합니다.

## 페이지 사용법

목록이 20개 이하이면 기존처럼 출력 후 메뉴로 돌아갑니다.
21개 이상이면 `1: 다음 쪽 / 2: 이전 쪽 / 0: 목록 닫기`를 입력합니다.
삭제 기능은 목록을 닫은 뒤 전체 문제 번호로 삭제 대상을 선택합니다.
